# What means to be a software engineer 

Software development is a very popular profession these days and the reason behind that is basically obvious: “almost all our world runs thanks to software”. Today it is very common to find devices that 20 years ago don’t have a processor inside, and today have more computational power than a personal computer on the 80\. Because of that and other many reasons, the world is asking for more and more software developers, but in the last few days, something about it is kind of broken. Then, I would like to invite you to travel with me on some thoughts about what does means to be a software engineer and why the industry seems to not have understood it yet. 

## The Industry misunderstood

I have developed mostly Android Native applications until now, which means that I know how to work with Java, Kotlin and the Android SDK. In those 9 years of software development I learned concepts like functional programming, reactive design pattern, observer/subscriber pattern, TDD, solid principles, and other more that I can apply when I’m developing those kinds of apps. If you read carefully many of those concepts are familiar in other frameworks and languages like react, react native, flutter and vue. Actually those frameworks are different between them, with their own APIs a way to work, but all of them are applying the same principles.

Each framework is itself a solution to a problem, each one of them have their own use cases where one is better than the other, but all of them are applying the same concepts, then, for a developer with a decent experience, change between those frameworks won’t be hard. In some cases would be a new language learning that could be done while the developer delivers value to the customer. For some reason, that is not so clear for the industry.

For example, if you are an Android Developer that makes apps using Kotlin, learning a new framework like spring to make backend won’t be hard. You already know the language, know the build system because you can use gradle as well, or you can learn maven if you like, you know Oriented Object Programming, and all the stuff I mentioned before, and of course you know the concept behind what an API Rest is. Maybe you have to learn about micro-services and containers, but you already know a lot of stuff. But you will be rejected if you don’t have that specific experience for the amount of time that the company you want to work for is asking.

In this scenery the meaning behind what it means to be a developer for the industry got reduced to “a guy that knows how to develop in a specific language and framework”. That idea is very far from what it means, that is “an professional capable of solving problems developing software”. That has to be the main goal of a software developer and more if you are a software engineer, “the problem solving”. 

The languages and frameworks are tools used by that professional to solve problems. Of course those tools have their own learning curves, but the complexity of the same would be proportional to the experience of that developer in the industry.   
 

## Then, if I learn a new framework and I don’t have any previous TI background, What am I?

The short answer would be a programmer, but it is a complex question to answer. The reason why it is complicated, is because a software engineer could learn by itself alone everything that needs to become one. The software development industry has tons of free resources that can be used to form new professionals, without the formal education of a collage, but that doesn’t imply that the collage is not relevant anymore.

Normally, if you can only follow instructions and solve very small and trivial problems, you can’t be considered a real software engineer, but if you can think on systems, and how those systems can be organized and related to solve problems, with abstractions, taking care of the scalability and the maintainability of the software on the time, you are a software engineer. A software engineer can program, but does more than that. 

A programmer coder, stays at a more basic level, that is still relevant and important, because to reach that basic level, a lot of knowledge needs to be accomplished first. If you read carefully until here, you can find no formal definitions about what is a junior developer vs a senior one, and that’s right, because if it is true that both face problem solving on their daily basics, it is not at the same level. Software developer then is more than code.

## Frameworks and languages

You have to know at least the name of frameworks like React or Vue, or listen the programming language names like Java, C\# or Kotlin. All those names are very popular, but at the same time could be enigmatic. I remember that I was having a talk with a college about how to continue his career path as software developer, and he was thinking too much about the problem that his main knowledge is focused on the backend development with C\#.

During this talk I mentioned to him, that he has more knowledge that he was conscious about, and I explain to him that C\# is:

* Strong type language  
* Supports OOP  
* Supports functional programming  
* Supports asynchronous programming  
* Supports abstractions and heritance

Then, now lets think in other language, for example Kotlin, this supports:

* Strong type language  
* Supports OOP  
* Supports functional programming  
* Supports asynchronous programming  
* Supports abstractions and heritance

We can do the same exercise with 2 or more languages and almost all of them would include the same support. Of course each language has its own spice that makes it the best solution for some kind of problems, but at the end of the day most of them share a lot of concepts. Those concepts are an intersection of knowledge that you need to know no matter which kind of developer you are: backend, frontend, fullstack, mobile, web3, etc.

Then, if you are a developer in C\# making a transition to kotlin has to be an easy one. You will need some time to master Kotlin, but you can start to work on that language delivering value to the customer without being an expert on it. And the frameworks? They are quite similar. The framework despite the difference they have, they share a lot of concepts as well, for example react js and flutter are different frameworks with different initial purposes that share the reactive pattern as fundamental base of each one. 

To be very honest I’m oversimplifying the things with the frameworks, but as with the languages, you need to know a lot of concepts that can be translated to other frameworks with a little practice. The bad thing is that the industry doesn't understand this, and closes everything to a checklist where it is more important to know the technology than the concepts that are behind the same.

## The main principles

Then, what is the most important knowledge? I would like to talk about another chitchat I had with a colleague in the past about which kind of post-graduation was the best for his career as a software engineer. Being very honest, I was expecting to hear something like the MBA, Statistics, Data Analysis or similar, but he brings to the table a post graduation on *mobile multiplatform development*. 

I continued to listen to him about the programmatic content of the post graduation, and he was going to make mobile apps with react, angular using cordova and react native. At that moment I said NO very loud, and he was curious about why my position was so strong about it. Then, I proceeded to explain to him that the best kind of post graduation studies he could do were those based on abstractions and concepts, because those focused on technology knowledge, could have the potential to be outdated very quickly.  

Being very honest, our industry is still using technologies that we consider outdated and deprecated like cobol, are still in use, and It is not so clear when they are going to disappear, the reality is when the knowledge is strongly focused on the technology instead of the principles that make the same possible, this knowledge becomes less useful when the new hipped tech arrives. 

Then, in order to not become deprecated as a software engineer, focus your learning on abstractions, concepts or applications of those concepts, because the same will allow you to learn that new technology more quickly the next time this arrives. Remember that not learning the concept and focusing on the technology will become a tech debt with yourself that would need to be solved at some point of your career, then the best you can do is solve ASAP.

## Everything is about problem solving

When Uber was created the same solved a problem related with mobility, when Netflix was created solves a problem related with movies distribution, when Amazon was created solves a problem related with buying books and more on the internet. All those products solve problems that were not necessarily known problems at that time. For example, before Netflix everyone of us would rent a movie in places similar to Blockbuster, and everyone was comfortable with that, but Netflix made it easier and won.

Uber did almost the same, taxis still exist today, but it is more comfortable to use an app to call a taxi than make a phone call to do the same, and the best, avoid the necessity of money transactions between the taxi and the passenger. Before Uber everyone was used to calling a taxi, but that application made it better. In each one of those systems ruled by software problems would have been solved to make them real. The sum of all those solved problems: localization, payment processors, media collections, queue services and other more creates a join that makes them born and be loved by everyone.

Then yes, your software needs to solve a problem, since a simple calculation to find a partner, the software is always solving a known or unknown problem, that improves our life or apparently does it.

## The reason why is called software

This actually is something more related with some software engineers, and it is the fact that they forgot the great advantage of the software over the hardware, and it is that the software has to be easy to change. Yes, it has to be but more frequently than we can expect we are in front of legacy systems that no one knows how it works. Those systems look like a spell or ancient chant created by a forgotten wizard in a cave, and now it is your turn to keep that legacy intact for the generations. 

Changes in software is the norm, the software evolves with time, the software is migrated to new technologies or systems, some dependencies become deprecated and you need to replace them, the API’s in other dependencies change and you need to adapt your software to the new schema, and there are another more reasons why the software needs to be adjusted, but at the end of the day the software change. Our main goal is to make those changes easy, and this is more true today with generative AI, because if it is true that we can generate a lot of software with some direct instructions, making real scalable software requires critical thought.

And yes, the software is the soft part of every computational system, that piece that once left the production line we can adjust to that what we need, and for that reason needs to be simple to change.

## Then, what is a software engineer?

My short answer? Someone that solve problems with software, a more complex answer, from Roger Pressman on his book Software Engineering, he said: “Software engineering is a discipline that join methods, tools and procedures for the developments of the software on computers”\[1\], then a software engineer based on  that is the responsible to execute that. All is about problem solving and following conventions based on common sense and the engineering principles that allows to obtain software with good quality standards. It is not about learning a framework or hyped tool, it is about creating solutions that improves our life a little more each day.
